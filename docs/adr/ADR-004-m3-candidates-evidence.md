# ADR-004 — Milestone 3 candidates, claims and verification decisions

**Status:** Accepted · **Date:** 2026-10-29

1. **Migration 0003** adds `candidates.promoted_edition_id`, `organizer_domain`, `edition_key` and a unique index on `programs(organization_id, normalized_name)`. The 0001 schema had no link from a candidate to the edition it became.
2. **One confirmation path.** Only `verification.rules.verify_fact` can return `confirmed_official`, and only for facts that are `rule`/`structured_page` extractions, grounded verbatim (`ground_facts`), from a T1/T2, non-discovery-only source whose domain covers the evidence URL and shares a registrable domain with the programme URL, with an explicit, valid, plausible date. Feed hints, LLM output and manual entries are capped at `unverified`. In M3 only event dates and typed deadlines can be confirmed; titles, categories, formats and editions keys are descriptive and stay `unverified`.
3. **Dates:** own strict parser (`extraction/dates.py`) instead of `dateparser`, because the invariants forbid guessing. English and German month names; ISO, dotted, slash and textual formats; ranges. A missing year, invalid date, inverted range, month-only mention or `a/b/yyyy` with both parts ≤ 12 is *ambiguous*: it carries no date and goes to the review queue. Times of day are not parsed (`time_precision` is always `date_only`); `due_at_utc` and `source_timezone` stay NULL. The milestone date for every deadline type, including `application_open`, is stored in `due_date_local`; `opens_at_utc` is unused for now.
4. **Context classification** picks the nearest keyword in the same sentence/line (or the line above for headings), preferring specific types over a generic "deadline". Dates with no recognisable context are ignored (pages contain many unrelated dates). Classified-but-ambiguous ones are kept as unverified claims with a review item.
5. **Candidates and leads.** A candidate needs opportunity wording plus a date or application phrase (`discovery/candidates.py`). Auto-promotion happens only when the evidence is an official page from a T1/T2 source (pages crawled from that source, or feed/sitemap links fetched through the normal policy-aware fetcher). Feed-only, aggregator, community and manual candidates stay `new` leads; `radar candidates promote` records their facts as unverified.
6. **Identity and dedupe.** Fingerprint = sha256(`normalized_title | organizer_domain | edition_key`). Same canonical URL → same candidate. Same fingerprint at another URL → `duplicate`. Programme match: same URL+name, or same organization + identical normalized name (treated as a strong match). Similar-but-not-identical names (ratio ≥ 0.88) are held (`possible_duplicate_program`); the reviewer promotes with `--program ID` (merge) or `--new-program`. Different `edition_key` is always a different edition. An edition key is only taken from explicit evidence (title, URL, or event-date year); otherwise the candidate is held (`edition_key_unknown`).
7. **Changed official pages** re-enter verification (the candidate is not skipped when its page gets a new observation). A same-publisher change updates the value, keeps both claims and stamps `last_material_change_at`. A different publisher disagreeing → `conflicting_sources` + critical review; the stored value is not changed. Weaker evidence never overrides stored values; it only adds claims (and a medium review if it disagrees with a confirmed value).
8. **Chronology** (application_open ≤ close, event start ≤ end, close ≤ last event day) is enforced after each promotion; violations demote the involved confirmed deadlines to `unverified` and add a high review item.
9. **Review semantics.** `review accept/reject` records a human decision and never touches `fact_status`. Conflicts cannot be "accepted"; `review resolve --claim` may only choose a claim that is already `confirmed_official`.
10. **Application status** (`open/closed/not_open/…`) is derived only from confirmed dates; freshness windows follow LLD §10.3. `estimated_recurring` is never generated in M3.

**Known limitations:** sitemap URLs become candidates only if they match strong URL keywords and the page can be followed; follow-ups per run are capped by `max_pages_per_source_run`; `application_url` is not extracted; fees, funding and eligibility arrive with the LLM milestone.

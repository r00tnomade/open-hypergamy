# ADR-005 — Milestone 4: FreeLLMAPI-backed extraction

**Status:** Accepted · **Date:** 2026-10-29

1. **The model is advisory.** LLM output is validated against a strict Pydantic schema (`opportunity_extract.v1`, `extra="forbid"`), then every value is grounded: its evidence must cite a `segment_id` present in the exact payload and quote it verbatim (whitespace-folded only). Dates must be *contained* in their quote (parsed with the strict date parser), and a quote that classifies as a different kind of date (e.g. an event date offered as the application deadline) is rejected. Fee amounts must appear in the quote; formats need supporting words. Anything that survives becomes an `extraction_method='llm'` claim, which `verify_fact` caps at `unverified`. LLM facts are excluded from the "distinct values for a field" check, so a model cannot block rule-based confirmation, and a disagreeing LLM date adds only a medium review item.
2. **When it runs.** Only for candidates whose evidence is an official page (the same condition as auto-promotion), i.e. novel or changed pages. Feed-only, aggregator, community and manual leads never trigger a call, and `candidates promote` never calls the model. A per-run budget (`llm.max_calls_per_run`, default 20) and a response cache (`llm_cache`, key = sha256(model | prompt_version | schema_version | normalized input), volatile fields excluded) bound cost. Only schema-valid responses are reused; invalid ones are kept for diagnostics.
3. **Degradation.** Gateway down, timeout, 401/403/404/429/5xx, missing API key, missing acknowledgement, or an exhausted call budget raise `LLMUnavailable`: the candidate is promoted deterministically, marked `llm_state=pending` in its metadata, and `ohg run llm` drains the queue later (it stops at the first unavailability; exit 4 if anything is still queued). Malformed output is retried at most `llm.max_retries` (2) times, then recorded as `llm_state=invalid` with an `llm_invalid_output` review item. No other provider or profile is ever tried; the client module contains one loopback-only HTTP client, never follows redirects, and refuses to send a request containing the data directory, the API key or Telegram identifiers (privacy guard).
4. **Payload.** Allow-listed fields only (`source`, `observation`, `candidate`), segments chosen by relevance (dates/keywords) under a hard `max_input_chars` (12,000) budget on the serialized payload, after redaction of emails, phone numbers, credential-like strings, long tokens, local paths and tracking parameters. The schema is appended to the system message; page text appears only in the user message.
5. **Acknowledgement.** `ohg llm ack` records `{acknowledged_at, policy_version, provider, model}` in `<home>/llm_ack.json` (0600). It is required before any FreeLLMAPI request and invalidated when `POLICY_VERSION` changes; the `local` provider needs none. `ohg init` shows the same checklist but does not record it. `ohg doctor` and `ohg llm status` report reachability, acknowledgement, key presence and whether the `auto:ohg-free` alias is listed, using only `GET /models`; they state that free-only routing is operator-attested.
6. **Not materialised:** LLM-proposed event dates, format, location, fee, funding and eligibility are stored as claims only; edition columns change only for confirmed facts. Eligibility assessment and scoring that consume these claims arrive in M5.

**Known limitations:** the LLM's `title`/`organizer`/`edition_key` are ignored when identity is already derived deterministically (organizer and edition_key are recorded as claims only); the segment selector is heuristic, so a long page may omit a relevant paragraph; behaviour against a real FreeLLMAPI gateway is untested (all tests use a scripted loopback transport), including whether `auto:ohg-free` appears in `/v1/models`.

# ADR-007 — Milestone 6: operations (reports, calendar, scheduling, backups, catch-up)

**Status:** Accepted · **Date:** 2026-10-29

1. **Migration 0005** adds `sources.portfolio` (one of the HLD §6.2 classes) so coverage can be reported against the ~200 target by class. Targets are constants (`PORTFOLIO_TARGETS`); only actual counts are ever reported.
2. **Source seeding.** `config/sources/*.yaml` are the eight LLD batch files, deliberately **empty**: this tool cannot verify real URLs, robots rules or site terms, and the LLD forbids placeholder domains. `ohg sources probe FILE` (live robots/fetch/parse check, writes nothing) and `ohg sources audit` (policy review, staleness, failures, portfolio vs target; exit 4 if issues) support adding reviewed batches of ~10.
3. **One "today".** Date-only deadlines have no timezone, so all deadline arithmetic (promotion, scoring, sentinel, reminders, reports, `deadlines`, `--within`) uses the user's local calendar date in `app.timezone` (default Europe/Berlin) via `clock.local_today`, not UTC. Timestamps remain UTC.
4. **Reports** (`reporting/`): `weekly` is one query layer with two renderers (Markdown file, plain-text Telegram digest), so they cannot drift. `changes` is read-only (new editions, moved deadlines from claim history, priority changes, reviews, alerts, failures). `sources` shows real configured/enabled/healthy counts per portfolio. Files are written 0600 under `<home>/reports/`.
5. **`.ics`** is hand-written RFC 5545 (CRLF, 75-octet folding, escaping, stable UIDs). Event dates, application windows, deadlines and prep tasks are separate items (`EVENT`, `APPLICATION-WINDOW`, `DEADLINE`, VTODO `PREPARATION`). All dates are all-day `VALUE=DATE`, never 23:59 or a timezone. Only confirmed dates by default; stale ones are labelled `(stale: recheck)`; estimates and unverified dates only with an explicit flag and a visible label; conflicting dates are never exported. The application-window title carries the labels of both ends.
6. **launchd** (`scheduling/launchd.py`): one LaunchAgent per job (sentinel daily, discovery weekly, digest weekly, backup daily; times in `schedule:` settings), absolute `ohg` path from the *virtualenv* (`sys.executable` is deliberately not resolved, or the venv is lost), `WorkingDirectory=OHG_HOME`, a minimal environment, `OHG_TRIGGER=launchd`, and **no secrets**. Install uses `launchctl bootstrap gui/$UID` and only ever touches `com.openhypergamy.*` files.
7. **Secrets** (`keychain.py`): environment first, then the macOS Keychain (service `OpenHypergamy`, `ohg secrets set|status|delete`), disabled with `OHG_USE_KEYCHAIN=0`. Values are never printed or logged. Limitation: `/usr/bin/security` takes the value as an argument, so it is briefly visible to the same user in the process list during `secrets set`.
8. **Job tracking and catch-up:** every scheduled job (`discovery`, `sentinel`, `digest`, `backup`) writes `job_runs` with its trigger; an unrecognised `OHG_TRIGGER` counts as manual. A job is *expected* if its LaunchAgent is installed or it has run before; it is *overdue* when its last success/partial run is older than its allowance (`schedule.*_max_age_*`) or it never completed. `ohg status`, the digest and the report list overdue jobs. `ohg run all` and `run sentinel` queue one `monitoring_gap` alert per gap (keyed by the last-success date) **before** running, then run sentinel logic first against the current time, then discovery, deferred LLM work, scoring and alerts; the existing idempotency keys and the "most urgent threshold only" rule prevent a flood of stale reminders.
9. **Backups:** files are standalone (`journal_mode=DELETE`, no `-wal`/`-shm`; a read-only open of a WAL backup used to leave sidecar files behind). `db backup` verifies the file, records a `backup` job and applies retention (newest per day for `backup_keep_daily` days, newest per ISO week back `backup_keep_weekly` weeks, nothing older, the newest always kept; `pre-migration-*` files are never pruned). `db restore --check` verifies and records the check (shown in `status`); `db restore --to NEW` restores into a new file and refuses to overwrite anything, including the live database. Replacing the live database is intentionally manual.

**Known limitations:** no real source URLs are seeded; the monthly strategic review is a manual `report weekly`/`report changes --since 30d`; iCal/Playwright adapters are still not implemented; plists were generated and parsed but never loaded into a real launchd in tests; the Keychain path was exercised with a fake `security` runner only; the Telegram and LLM integrations have not run against the live services.

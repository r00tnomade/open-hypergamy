# ADR-006 — Milestone 5: eligibility, scoring, actions, sentinel, Telegram

**Status:** Accepted · **Date:** 2026-10-29

1. **Migration 0004:** `editions.action_locked` (manual `set-action` wins over the planner until `auto`), `score_snapshots.profile_version`, `notification_log.message_text` (a retry needs the body; `message_preview` stays a 160-char preview).
2. **Profile** (`profile.py`): strict Pydantic, found via `$OHG_PROFILE`, `<home>/profile.yaml`, then `config/profile.yaml` (all git-ignored). It is read only by local code: scoring, eligibility and message *selection*. It is never in an LLM payload (the privacy guard and tests check this) or in a Telegram message. No profile → scoring and alerts are skipped with a hint; fetching and verification still work.
3. **Eligibility** (`verification/eligibility.py`): requirement *text* comes from grounded claims (usually LLM-extracted); the *decision* is by explicit rules over degree level, year of study, institution country, subject; citizenship and age are always `unclear` because the profile stores neither. A blocker that will clear later (higher degree stage, minimum year not yet reached) → `future_cycle`; any other blocker → `ineligible`; a requirement the source marks non-blocking never blocks. No statement at all → `possibly_eligible` ("absence is not proof"). Unresolved recognised criteria (profile data missing) → `needs_review`. Each change appends an `eligibility_assessments` row with the profile version.
4. **Fit** = 30/25/20/15/10 weighted components (settings `scoring.weights`), each 0–100 and rule-based (`scoring/fit.py`, version `score-v1`). Funding/fee/format/location inputs are LLM claims (unverified), so `FUNDING_CONFIRMED` can only fire for a confirmed claim, which cannot currently exist. **Urgency** (`urgency.py`) uses only confirmed deadlines; unverified → 10, stale/conflicting → 40 with a reason code; a passed deadline is "closed" (0), never "stale". Band rules, the medium cap for unresolved eligibility, and `excluded` for ineligible are in `scoring/actions.py`. Snapshots are appended only when something changed.
5. **Actions:** the planner moves `user_action` only among apply/prepare/monitor/future_cycle (and revives an `archived` edition it archived itself when eligibility changes). It never touches applied/accepted/rejected/withdrawn or locked editions, never archives because a date passed, and does not demote apply/prepare because a date went stale. Action items use `action:{edition}:{type}:{deadline|none}:actions-1`; open items that no longer apply are dismissed; done/dismissed items are never recreated.
6. **Freshness and the sentinel:** `refresh_edition` only renews `source_fresh_until` when a page was actually just verified (`verified_now`). The sentinel (`ohg run sentinel`) marks lapsed confirmed deadlines `stale` (value kept), then re-fetches the *evidence pages* of editions with a deadline in the next 90 days (`monitoring/recheck.py`): byte-identical or 304 → freshness renewed and `stale` restored to `confirmed_official`; changed → normal verification; failed → stays stale and is reported (exit 4). Re-checking the source index would not work because an unchanged page yields no new observation.
7. **Alerts** (`monitoring/deadlines.py`, `notifications/`): new verified high-fit opportunity, application open, 30/14/7/2-day reminders (critical/high band, apply/prepare, confirmed dates only), moved deadline, conflict/stale on a high-fit opportunity, repeated source failure behind a near deadline (power-of-two streak buckets), weekly digest. Catch-up sends only the most urgent crossed reminder threshold and records the older ones as `suppressed`. Every alert has the official link and a certainty label; estimates are labelled "NOT confirmed". Keys: `new:`, `opened:`, `deadline:{edition}:{deadline}:{offset}:{due}`, `moved:`, `stale:`/`conflict:`, `sourcefail:`, `digest:{ISO week}:{part}`.
8. **Outbox:** a `pending` row is written before sending; `sending` → `sent` | `pending` + `next_retry_at` | `failed`. Transient errors back off (or honour Telegram's `retry_after`) up to `telegram.retry_limit`; bad token/chat → `failed` immediately and visible in `ohg status`; `notify retry --include-failed` re-queues. Per-run cap `maximum_messages_per_run`: critical types go first and are deferred (never dropped); new/opened alerts over the cap become `suppressed` ("grouped into weekly digest"). Rows stuck in `sending` for 10 minutes are retried (at-least-once; one duplicate is possible after a crash between Telegram's reply and the local update). `telegram.enabled: false` stops queuing and sending entirely. Telegram errors never contain the token.

**Known limitations:** no age/citizenship/visa data, so those requirements always need a human; subject matching is exact-word; region detection is a small keyword list; duration and effort are not modelled in `time_cost` or urgency; `config/scoring.yaml` from the LLD is not implemented (weights come from `settings.yaml`, thresholds are code constants); the sentinel only re-verifies pages that produced a promoted edition; `refresh_edition` marks application status `unknown` while a close date is stale; real Telegram delivery has never been run.
